# Schedule Refresh & Live Platform Info — Implementation Notes

This document describes the implementation that landed for TODO #3 plus the
related schedule-refresh work. It supersedes the earlier proposal.

## Two cadences, two mechanisms

| Data | Cadence | Source | Where it lives |
|---|---|---|---|
| Schedule (times, train numbers, station pairs) | Weekly | Israel MOT GTFS | `www/rail_times_index.json`, regenerated by CI |
| Platform numbers | Per-trip, day-of | rail.co.il `searchTrain` API | Pre-fetched at submit time, shown on the confirmation page |

Platform info is **not in the GTFS** for Israel Railways — verified directly:
all 70 rail stops have empty `parent_station`, empty `stop_desc`, and no
`platform_code` column. Each station is one stop. `searchTrain` is the only
source, and platforms get reassigned operationally, so this needs to be live
rather than baked into the JSON.

## Schedule refresh

### CI build — `scripts/build-schedule.js` + `.github/workflows/update-schedule.yml`

- Cron: Mondays 04:00 UTC, plus `workflow_dispatch` for manual runs.
- Downloads `https://gtfs.mot.gov.il/gtfsfiles/israel-public-transportation.zip`.
- Filters to `agency_id=2` (Israel Railways) and weekday services (Sun–Thu).
- Maps GTFS `stop_code` → rail.co.il station ID via a hardcoded table in the
  script. Add new stations there when MOT publishes them; the script logs a
  warning naming any unmapped stop.
- Emits only pairs anchored on Jerusalem (`stationId 680`) — matches what
  the app reads (`app.js:212-214`).
- Adds `generatedAt` so the app can compare freshness.
- Validates output before writing: schema, ≤10% station drop, ≤20% pair
  drop, time format `^\d{1,2}:\d{2}:\d{2}$`, no dup train numbers per pair,
  arrival ≥ departure. Any failure exits non-zero — the workflow fails and
  no PR opens.
- Opens a PR (not a direct push) on real changes. Diff summary lives in the
  PR body.

To run locally:
```
npm run build-schedule -- path/to/gtfs.zip www/rail_times_index.json
```

### Browser — non-blocking remote refresh (`www/app.js`)

`loadData()` reads the bundled JSON instantly. After that:

1. If `localStorage.scheduleCache` has a newer `generatedAt`, apply it.
2. Fire `fetch(REMOTE_SCHEDULE_URL)` against jsDelivr (10s `AbortSignal.timeout`).
3. Validate the response via `isValidScheduleShape` (same rules as CI).
4. If newer and valid, persist to `localStorage` and re-render the dropdowns —
   **only if `state.step === "form"`**, so the UI never gets yanked from
   under a user mid-OTP or viewing a result.

Anything that fails validation is logged and dropped. The bundled JSON is the
safety net.

`REMOTE_SCHEDULE_URL`:
```
https://cdn.jsdelivr.net/gh/yomach/train_ticket@main/www/rail_times_index.json
```

## Live platform info (Part F)

### Worker change

`cloudflare-worker/worker.js` now takes the host root as its upstream
(`https://rail-api.rail.co.il`) and passes the URL pathname through verbatim,
so both `/common/api/v1/Otp/Send` and `/rjpa/api/v1/timetable/searchTrain`
get proxied. App-side callsites prefix their paths accordingly (`sendOtp`,
`verifyOtp`, `orderSeat`).

`searchTrain` is `POST /rjpa/api/v1/timetable/searchTrain` with a JSON body
(`fromStation`, `toStation`, `date`, `hour`, `scheduleType: "ByDeparture"`,
`systemType: "2"`, `languageId: "Hebrew"`). Returns `result.travels[].trains[]`
with `originPlatform` / `destPlatform` per leg; we look up by exact
`trainNumber` identity. `shouldServeStatusPage` was narrowed to GET-on-root
(or `/health`) so non-root GETs aren't intercepted as status probes.

### Pre-fetch on submit

`handleSubmit` kicks off `fetchPlatformInfo(state.tripParams)` the moment
the user clicks הזמן, **before** the first `orderSeat` attempt. The promise
is stored in `state.platformInfoPromise`. On the OTP path it races with SMS
delivery and user input — by the time `showResult` runs, it's almost always
already resolved.

`state.platformInfoTripKey` (built from `tripKey(state.tripParams)`)
fingerprints the trip so stale results from a previous submit can't bleed
into a fresh booking. `handleReset` clears both fields.

### Confirmation rendering

`showResult` awaits the in-flight promise, validates platform numbers (1–50),
and writes a single line:

- Boarding platform: `עליה מרציף N`
- Destination platform: `ירידה ברציף M`
- **Jerusalem arrivals only**: append exit-side based on parity —
  odd platforms (1, 3) → `לצד ימין עם כיוון הנסיעה`,
  even (2, 4) → `לצד שמאל עם כיוון הנסיעה`.

Any failure (network, malformed response, out-of-range platform, mismatched
train number) leaves `#platformInfo` hidden silently. The QR is the
load-bearing artifact — it must always render.

### Guardrails (runtime)

- `extractPlatforms` requires `String(train.trainNumber) === String(trainNumber)`.
  No fuzzy match.
- `sanitizePlatform` requires `Number.isInteger(n) && 1 ≤ n ≤ 50`.
- One retry on 5xx or transient network errors; silent thereafter.
- 8s `AbortSignal.timeout` per attempt.

## Shared helpers

`isValidScheduleShape`, `sanitizePlatform`, `extractPlatforms`, `tripKey` live
in `www/schedule-helpers.js` (UMD-style, like `booking-helpers.js`) so they
can be unit-tested from Node without a DOM. See `tests/schedule-helpers.test.js`.

## Version check (Part J)

`checkVersion` (`app.js`) moved from GitHub's REST API to jsDelivr's package
metadata API:
```
https://data.jsdelivr.com/v1/packages/gh/yomach/train_ticket
```
GitHub's 60-req/hr unauthenticated limit was a poor fit for a public app on
shared mobile NATs. jsDelivr has no such limit. The "latest version" link is
now constructed from the tag (jsDelivr's metadata doesn't include a release URL).

## Other UX (Parts G, H, I)

- **Trip summary on confirmation** (`#tripSummary`): `<from> ← <to> • <date>
  <time> • רכבת <num>`. Looks up station names from `state.stations`; falls
  back to IDs if the lookup fails.
- **OTP confirm button gating** (`#otpConfirmBtn`): starts `disabled`, toggles
  on `input` events from the OTP field. Reset to `disabled` whenever the OTP
  step is entered.
- **OTP auto-continue**: when Android's SMS User Consent plugin fills the
  OTP, `armSmsAutoFill` waits 600 ms (long enough to display "מולא אוטומטית,
  ממשיך…") and then triggers `handleOtpConfirm`. Guarded by `state.step ===
  "otp"` and `!disabled` so a user backing out cancels the auto-submit.
  Browser builds are unaffected (the SMS Consent plugin is native-only).
